# Diagnostic contracts: bounded repair, grain and OWL explanations

The user approved implementation of the three recommendations after the v0.12.0 research. Build working opt-in diagnostics, preserving default verification semantics and source confidentiality. Do not publish or add runtime dependencies. Use the existing Python3.11+, pySHACL, owlready2/HermiT and PostgreSQL read-only interfaces. Ideas from the reference projects are reimplemented; no external source is vendored.

## Approach and scope

Three independent diagnostic paths keep risky experiments out of default checks. A new solver/semantic engine would add unresolved runtime/license costs; attaching an all-purpose theorem prover would promise coverage we do not have. Retain current check statuses and not_proven boundaries.

1. `shacl-repair --spec FILE [--timeout-ms 30000]` is a standalone authored synthetic fixture stage (`shacl_repair`). It validates supported class/numeric-range/property-pair shapes on independent before/after data, verifies explicit retained targets and immutable edits, and compares literal expected normalized report facts. A target removed to make a report empty cannot satisfy a retained-target obligation. Hard prohibitions are distinct from soft edit costs. Read trusted local fixture files only, with bounded input/process execution and no network RDF imports. Output counts/opaque ids/hashes only, never RDF values/paths. Unsupported profile or incomplete validation must not pass. Before/after fixture execution must be real pySHACL, not a report-only simulation. Provide synthetic runnable examples including legitimate repair and target-deletion evasion. This is diagnostic fixture validation, not automatic repair or an operational write.
2. `grain --config FILE --spec FILE [--max-rows 100000]` (`grain`) checks independently authored intended measure grain/key provenance for the existing undated preaggregate-to-node join fragment. It derives actual operations from cfg, compares independent source/group/output/key/null-policy claims, and checks actual source/node key assumptions, fanout/orphan/null exclusion evidence with read-only bounded PostgreSQL queries. Avoid a label-only comparison: include operation/key provenance and actual key/row checks. Date/closure/multi-hop/general-DAG claims are explicitly unsupported. No configuration mutation, source DDL or new Cube engine. Report exact scope and preconditions, no theorem/business-truth claim. Synthetic PostgreSQL tests cover duplicate key, missing referenced node, NULL by exclusion and wrong independently declared grain.
3. `reason --explain-inconsistency [--explain-max-axioms 128 --explain-max-checks 64 --explain-timeout-ms 10000]` attaches a bounded same-HermiT inconsistency explanation only after owl:consistency failed. New owl_explain module handles deterministic axiom groups, local process deadlines, subset removal and config_ref mapping. Claim subset-minimal only after every retained candidate deletion was checked and all required checks completed; a stopped search may yield a sufficient partial core, never a minimality claim. Preserve the original failure; consistent or excluded OWL does not invoke it. Same reasoner is not independent certification, and no global minimum/unique/complete explanation is claimed. Do not vendor LGPL Java code or require OWLAPI wiring. Never print raw assertions, raw keys or Java stderr. Actual HermiT tests must establish a real no_children/disjoint inconsistency and budget/error controls.

## Interfaces and ownership

Root owns `skills/semantic-crosscheck/scripts/sxc.py`, top-level README/CHANGELOG/design/skill/command catalog integration, end-to-end CLI tests and final integration. Feature implementers own only their new modules, dedicated tests/examples/docs. OWL implementer additionally owns owl.py and stage_reason.py. New stage modules expose `run(cfg,args,out:Path)->Result`; standalone shacl cfg is None. Outputs write through existing CLI Result flow; no default pipeline additions. Module input validation must guard output/input aliases and stale artifacts before writes.

## Acceptance

Default unit/available integration checks retain behavior. New features have red-to-green regression evidence and real optional-runtime tests. Strict schema parsing, limits, duplicate JSON keys/nonfinite numbers, unknown/unsupported claims, failures, empty/vacuous scope and secret/path non-disclosure are tested. New CLI help/docs agree. Independent final review reruns targeted checks; whole suite, compilation, leak scan and clean local integration are completed. No remote push/release without the later deployment request.
