# semantic-crosscheck v0.11.0

Release date: 2026-10-27. A minor release adding two opt-in checks, both off by default: a SHACL comparison of
column-pair rules and an existence witness for keys that standalone Cube answers leave out. The W3C corpus profile
grows to cover the SHACL parameters the first check generates.

## What it is

semantic-crosscheck generates PostgreSQL hierarchy closures, SQL and SHACL rules, OWL/HermiT reasoning
and a Cube semantic layer from one configuration, then compares their results and hand-written gold SQL.
This release lets one more kind of rule reach SHACL and gives sparse sampled pair tests a separate, bounded
source of existence evidence. Without the new options every existing check and output is unchanged.

## Highlights

- **SHACL property pairs (`verify.shacl_pairs = true`).** A shape whose only constraint is an `sql_violation` of
  exactly `t.<a> <op> t.<b>` (`>`, `>=`, `<`, `<=`; two different plain column names, no comment, cast,
  parenthesis, constant, `=` or `<>`, and no `path`, `class` or bound on the shape) is translated at reason time
  into a SHACL property shape with `sh:lessThan` or `sh:lessThanOrEquals`. The separate check `shacl:pair:<id>`
  passes when pySHACL's focus nodes on a separate pair export equal the keys in `v_shape_<id>`; disagreements fail
  as `shacl_only` or `sql_only`. The pair shapes pass the generated-shape preflight first and are never written to
  `build/shapes.ttl`, so its comparison and every `shacl:<id>` check stay as they were. Both columns must be of the
  base types `smallint`, `integer`, `bigint` or `numeric` without NaN or infinities, and the target keys unique;
  otherwise the check is `not_run` (`column_type`, `non_finite_values`, `duplicate_keys`). Pair rows count against
  `verify.shacl_max_rows` (`resource_limit`).
- **Existence witness (`verify.existence_witness = true`).** Each sampled or chunked V3 pair test gains a separate
  check `v3w:pair_witness:<member>+<member>`. For every asked key that Cube's together answer holds but an alone
  answer leaves out, PostgreSQL is asked whether the measure has a row satisfying its configured `where_sql` (for
  the closure `qty`, a closure row), binding the texts Cube's equals filter receives: once in the key-read
  REPEATABLE READ snapshot and again after the Cube queries. No row and an empty (NULL) together value pass
  (`absent_no_facts`); a row in both reads (`absent_with_facts`) or no row with a non-empty together value
  (`witness_value_mismatch`) fail. A key missing from the together answer, a failed cast, another failed statement
  or a change between the two reads leaves the check `not_run` (`witness_incomplete`); a witnessed pair test that
  errors after its key read leaves it `not_run` (`pair_error`). Details hold counts only, never keys.

## Changed

- `shacl-corpus --w3c-suite` profile: `sh:lessThan` and `sh:lessThanOrEquals` with an IRI value on property shapes
  are now in profile. On the pinned suite `core/property/lessThan-001`, `lessThan-002` and `lessThanOrEquals-001`
  run (9 of 98 entries instead of 6), and pySHACL 0.40.1 and Apache Jena 6.2.0 both matched their expected reports
  (observed 2026-10-26). No option controls this: the stage's default result on the pinned suite gains six passing
  checks, and the stage as a whole still cannot pass because 89 entries remain `not_run`.

## What a pass shows

- `shacl:pair:<id>` passing means pySHACL and the SQL view point at the same rows on one snapshot. It does not
  show that the rule is the right business rule, and other `sql_violation` forms remain compared in SQL only.
- `v3w:pair_witness` passing means the keys an alone answer left out have no qualifying source row under the
  configuration's own filters, and their together value is empty. It does not show data completeness, does not
  check keys an alone answer holds, does not validate the filters in `crosscheck.toml` themselves and does not
  cover the NULL key group.

## Compatibility and migration

Both options default to `false`; with them off every output is unchanged, and no new package or dependency pin is
required. The W3C corpus profile change applies without an option, as described above.

With `verify.shacl_pairs = true` and a pair-form shape configured, `reason` needs rdflib and pySHACL (exit 3) and a
`build/shapes.ttl` that matches the configuration (exit 2), even when no other shape is compared. While a pair
check is `not_run`, `reason` and `report` cannot pass: change the column type or the data, or set
`verify.shacl_pairs = false`.

Rerun `build`, `reason`, `cube`, `verify` and `report` after upgrading because the engine fingerprint changes.
Installing the release neither reruns stages nor certifies old evidence.

## Known limitations

- pySHACL 0.40.1 orders NaN and mixed datatypes unlike SHACL and PostgreSQL, so property pairs compare only the base
  numeric types `smallint`, `integer`, `bigint` and `numeric` without NaN or infinities; a domain over them, other
  types, non-finite values and duplicate target keys are `not_run`, never a pass. A `not_run` pair check blocks a
  passing `reason` and `report`.
- The witness is one-directional and V3-only: it reads only keys an alone answer left out, runs only for sampled or
  chunked pair tests (the unfiltered path at or below 2,000 keys gets none, not even when it errors) and is not run
  by V4 replays. Its two PostgreSQL reads bracket Cube's queries but share no snapshot with them.
- The pair test's own status, detail, D95 bound and V4 role are unchanged, also when the witness passes or fails:
  an incomplete sample still claims no D95 bound, and V4 does not use witness evidence.
- Existing [v0.10.0 limitations](v0.10.0.md#known-limitations) still apply.
