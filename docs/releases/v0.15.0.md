# semantic-crosscheck v0.15.0

Release date: 2026-11-01. A minor release adds optional authored-source version
bindings, selected metadata-only OKF exchange and a fixed offline evolution
diagnostic. Dependency pins, default pipeline stages and operational report
requirements stay unchanged.

## What it is

semantic-crosscheck generates PostgreSQL hierarchy closures, SQL/SHACL rules,
OWL/HermiT reasoning and a Cube semantic layer, then cross-checks them against
each other and independently authored gold SQL. The new opt-in paths track the
local business definition behind authored expectations, exchange bounded
contract metadata and test how existing guards behave across source changes.
Source currency, profile completion and synthetic replay never establish
business truth or operational PASS.

## Highlights

- **Authored source bindings.** An authored `gold.expect` may declare the closed
  `spec_source` table with a project-relative file and a SHA-256 pin, plus optional
  caller labels. Missing, changed, blocked and unavailable evidence are distinct.
  Noncurrent evidence stops fixture cases before DB access; completion drift
  demotes affected passing cases to `not_run` while preserving failures/errors.
  Existing unbound cases retain their behavior. No text parsing, object-existence
  claim, approval inference, grain extension or new report authority is added.
  See [source scope and bounds](../knowledge-sources.md).
- **Selected OKF metadata exchange.** `okf --export DIR --select GOLD_ID` requires
  explicit selection and configuration; `--import-preview DIR` validates the
  closed `sxc-verification-contract-metadata/v1` profile against current trusted
  local inputs. The bundle uses OKF 0.2 and custom type `SXC Verification Contract`.
  It contains IDs, counts and hashes, omitting source/SQL text, rows, parameter
  values, DSN names, paths and runtime receipts. No imported verdict or executor
  is applied. Existing destinations are never overwritten. Unsupported profile
  and changed trusted inputs remain different outcomes. See the
  [profile and no-clobber publication contract](../okf.md).
- **Fixed offline evolution replay.** `knowledge-evolution` uses a bundled bounded
  fixture and independent literal expectations across normal, changed, deleted,
  restored and retired source states. Its five checkpoints retain 26 contract
  slots through observation failures. Actual configuration, fingerprint, source
  capture/finish and report APIs operate on temporary synthetic files and fixed-time
  in-memory receipts. Exact restoration can be current without promoting retained
  `not_run` evidence. Retiring cases changes configuration and stales old synthetic
  operational receipts. No DB, engine or model executes; semantic coverage is not
  measured. See [offline replay](../knowledge-evolution.md).
- **Input-preserving publication.** The shared result writer uses a unique,
  exclusively created temporary file, preserving pre-existing fixed `.part`
  hardlinks. Source-bound expectation and OKF error/cleanup paths lose write
  authorization after observed configuration drift. Preview retains the inventory
  tied to validated bytes through final publication. Windows junction fixtures
  remain real Windows tests and are registered only on that platform, rather than
  creating unavoidable skips in the strict Linux integration job.

## Compatibility and migration

All three additions are opt-in. Existing unbound authored expectations and the
operational `build`, `reason`, `cube`, `verify`, `report` pipeline retain their
scope. `spec_source` is supported only for authored expectation cases; captured
cases reject it. Pin actual file bytes and change a pin only after reviewing the
definition. A matching hash does not approve the definition's meaning.

Both OKF modes need `--config`; export also needs repeatable `--select`. Preview
does not apply definitions. `knowledge-evolution` rejects `--config`, ignores cwd
configuration and accepts no external fixture or engine selector.

Rerun operational stages after upgrading: the engine fingerprint changes with
the package. Installing the release neither reruns stages nor refreshes evidence.
The new diagnostics never substitute for independent business expectations or
operational runtime checks.

## Checksums

Download `semantic-crosscheck-0.15.0.zip`, `verification.json` and `SHA256SUMS`
from the release. Verify both listed SHA-256 values before unpacking. The ZIP
contains exact tracked Git blobs at the published commit, excluding ignored local
state. Hash identity is not bundle authenticity or business-rule certification;
byte-for-byte ZIP reproducibility across timezones/toolchains is not claimed.

After publication, `gh release verify v0.15.0` and
`gh release verify-asset v0.15.0 <file>` verify the immutable release and asset
attestation. Fresh downloaded bytes are separately compared with the expected
checksums and tracked Git inventory.

## Known limitations

- Source filesystem protection observes boundaries. It is not a continuous lock,
  hostile-ancestor sandbox or ABA-proof guarantee. Caller labels are declarations,
  not parsed objects or approval evidence.
- Only the closed metadata producer profile is supported. General OKF may be valid
  but unsupported. Hash integrity is not authenticated origin; runtime execution,
  cross-layer correctness, authenticity and import application stay `not_proven`.
- If publication has completed before drift is detected, the operation can fail
  while leaving the destination. Lost configuration authorization can likewise
  leave owned staging intact to preserve newly declared inputs. Inspect it and
  run a fresh preview before use; caller destinations are never automatically deleted.
- The evolution diagnostic covers its fixed synthetic harness contracts. It
  measures neither semantic coverage, business effectiveness nor real engine
  correctness, and it does not add a product retirement/tombstone policy.
- Unit exclusions and Windows-host local results do not establish unexecuted
  platform/engine behavior. Public CI evidence reports actual coverage separately.
- Existing [v0.14.0 limitations](v0.14.0.md#known-limitations) continue to apply.
