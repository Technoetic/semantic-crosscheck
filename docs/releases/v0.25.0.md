# v0.25.0 — disclosed empty comparisons, corrected pattern and date-window guidance

Release date: 2026-11-14.

## What it is

This release discloses passes that compared empty sets in three generated checks, corrects what the documentation
says about the data-rules pattern subset, and corrects the advice for gold date windows on `timestamp` columns.
Statuses, check ids, exit codes, the verify evidence object, its schema and the evidence rule version do not change.
It adds no runtime dependency, configuration key, CLI stage or research reference.

## Highlights

### Empty comparisons are disclosed

A comparison of two empty sets passes without having compared anything. Until v0.24.0, among the checks between
generated layers, only a defined class without members said so (V1 and V2 comparisons with no row, empty strata and
an empty closure-oracle graph were already disclosed). Now these passes say it too:

- `shacl:<id>`, and `shacl:pair:<id>`, which compares two key sets the same way, when neither pySHACL nor the SQL
  view flagged a key. One NOT PROVEN line per reason run names these checks (up to ten, then a count) and says that
  a pass then shows only that neither engine flagged a row of this data, not that both would flag the same violating
  row. It names again the checks whose export held no row at all (`group_rows` 0; for a pair check `rows_exported`
  0, which counts the whole pair export of the run).
- `v5:closure:<h>` when neither OWL nor SQL has a closure pair: "the hierarchy has no closure pair in OWL or in SQL,
  so the comparison holds vacuously".
- A V3 pair test that passed without comparing a key: one line per verify run names these tests (up to ten, then a
  count). With the modes as they are, only an unfiltered test (at most 2,000 keys) can pass that way, when Cube's
  together answer holds no key; its alone answers may still hold keys (`alone_only_keys`, which is no failure).

Each of these passes carries `empty: true` in its detail. On the SHACL and closure checks that is the key V1 uses
for a comparison with no row on either side; on a pair test it means that no key of the together answer was compared
by value, while the alone answers may hold keys. A `v5:defined:<name>` check without members now carries the key too
(its line is unchanged). A non-empty pass and a fail are unchanged, and the verdicts are the same with
`verify.gold_observation = "require"`. `report.md` lists the new lines with every stage's lines.

On the clean demo reason prints one more NOT PROVEN line, for the three shapes that clean data never violates, so
the quick start prints 19 NOT PROVEN lines instead of 18. Scripts that count NOT PROVEN lines see more.

### What the pattern subset guarantees

The `text_quantity` pattern subset makes Python's `re` and PostgreSQL's regular expressions read the syntax the
same way and refuses the constructs where they differ (alternation, letter escapes and others), as well as nested
repetition, over which Python's backtracking is exponential. It does not make them choose the same match: from the
leftmost position where a match starts, PostgreSQL takes the longest overall match (PostgreSQL 17 documentation,
9.7.3.5 "Regular Expression Matching Rules") and Python the first one its backtracking finds.
`([0-9]+)(?:[0-9]g)?` on `123g` captures `12` in PostgreSQL and `123` in Python. When such a difference changes the
rule's output (which rows it flags, or their numerator or divisor), `rule_xcheck:<id>` fails and `rule:<id>` is
`not_run` (`paths_disagree`), never a pass; a difference that changes no output leaves the verdict the same under
either reading. PostgreSQL 17 tests now pin both cases. Keeping neighbouring items disjoint, or anchoring a pattern
whose match is the whole text, avoids the difference of this example; it is not shown to avoid every difference.
See [the data-rules reference](../data-rules.md#pattern-subset-text_quantity).

### Gold date windows on timestamp columns

`col BETWEEN CAST(:from AS date) AND CAST(:to AS date)` covers whole days on a `date` column. On a `timestamp
without time zone` column that holds times of day it ends at midnight at the start of the last day and leaves out
that day's later rows. The pitfalls reference now gives `col::date BETWEEN CAST(:from AS date) AND CAST(:to AS
date)` or the half-open `col >= CAST(:from AS date) AND col < CAST(:to AS date) + 1`, so that the gold window covers
the same whole days as the Cube date range.

## Known limitations

- An `expect` case whose sides are all empty is still not disclosed.
- The SHACL line names a check as having no row to check only when its whole export held no row (`group_rows` 0, for
  a pair check `rows_exported` 0). A shape whose target is empty while another entity of its value group has rows is
  named as flagging no key, not as having no row: no detail field says that its own target was empty. Likewise the
  `rows_exported` of a `shacl:pair:<id>` check counts the run's whole pair export, so a pair check whose own target
  is empty is named as having no row only when every compared pair entity is empty.
- The pattern subset still lets the engines choose different matches. The advice avoids the documented example's
  difference, not every difference; a remaining difference that changes the rule's output leaves the rule `not_run`
  (`paths_disagree`) until the pattern is rewritten.
- The date-window advice is documentation only; this release adds no check of how a gold query writes its window.
- The existing limits remain: checks between generated layers share the configuration's mistakes, measures have no
  independent recomputation, and gold, Cube and replay reads do not share a PostgreSQL MVCC snapshot.

## Corrections to earlier release notes

- [v0.22.0](v0.22.0.md), Known limitations, "Regex capture assignment", said: "The pattern subset keeps Python and
  PostgreSQL matches equal for the supported forms. Where the engines still assign a capture differently, the result
  is a false disagreement (`rule_xcheck:<id>` fails, the rule is `not_run`), never a false pass." The subset does
  not keep the matches equal: it makes both engines read the syntax the same way, but from the leftmost position
  PostgreSQL takes the longest overall match and Python's `re` the first one its backtracking finds, so within the
  supported forms the whole match can differ, not only the captures (`([0-9]+)(?:[0-9]g)?` on `123g` matches `123g`
  with capture `12` in PostgreSQL and `123` with capture `123` in Python). What the sentence says about the outcome
  holds when the difference changes the rule's output: the result is a disagreement (`rule_xcheck:<id>` fails,
  `rule:<id>` is `not_run`). A difference that changes no output leaves both outputs equal and the verdict the same
  under either reading, so it is never a false pass. That release's text is left as published.
