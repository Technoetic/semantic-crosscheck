# semantic-crosscheck v0.23.0

Release date: 2026-11-12.

## What it is

semantic-crosscheck compares PostgreSQL, SHACL, OWL/HermiT and Cube with
independently authored Gold SQL. This release is about what a pass means.
Every check now says what kind of evidence it is, a passing V4 mutant check
says what kind of item detected the mutant, the parts of measures and
hierarchies that no hand-written gold query covers are named, and a gold query
that compared no row is disclosed.

By default this is disclosure: check ids, check counts and exit-code rules do
not change (apart from the new exit 2 for an identifier that ends with a line
break), and statuses change only in one case (a gold query that contains
generated text). Both are under Compatibility and migration. An opt-in mode
turns the disclosures into statuses.

## Highlights

- **Evidence kinds.** Each check counts under one kind: `authored` (one side is
  a gold SQL file a person wrote, with no generated text in it), `recomputed`
  (recomputed from source rows by code that imports no generator; today the
  closure oracle `v3:closure_oracle:<h>`), `generated` (both sides come from
  `crosscheck.toml` through generators, including every other `v3:*` check and
  the OWL closure check `v5:closure:<h>`, whose two inputs are both generated),
  `structural` (one side) or `mutation` (V4). A check no rule names is
  `unclassified` and never counts as authored or recomputed. The kind says who
  or what produced each side, not that a side is right.
- **A V4 pass is no longer read as a gold detection.** A passing
  `v4:<operator>:<target>` means a replayed suite item failed against the
  mutant, and the suite also holds V3 items. The suite now runs authored gold
  items first, and each check records `detection`: `authored` only when an
  authored gold item failed, `generated_only` when every replayed authored item
  passed and a check between generated layers failed, `unattributed` for an
  item of no known kind, `none` for a survivor. In the default mode a
  generated-only kill gets a NOT PROVEN line with a remedy for its operator;
  in require mode the check fails instead (or is `not_run` when suite items
  were left out). On the clean demo 9 mutants are killed with an authored
  detection and 3 (`measure_agg_to_max` of `firm_open`, `on_hand` and
  `consigned`) by generated checks only.
- **Facets without authored evidence.** On full-scope verify runs every facet
  of a measure (its value, its date, its joins), a hierarchy (closure members,
  ancestor and descendant cubes) and the class column is `compared` (by an
  authored gold query, with rows that hold values), `detected` (by an authored
  mutant kill), `accepted` (`verify.accepted_gaps`) or a gap with a reason
  (`not_in_model`, `no_values`, `no_rows_compared`, `gold_not_run`,
  `generated_text`, `filter_only`, `no_gold_reads`). In the default mode each
  element with a gap gets one NOT PROVEN line; in require mode its
  `gold_evidence:<element>` check takes that place. On the clean demo 15 of
  17 facets are compared, 1 is detected and `part+m_firm_open` has no
  authored evidence (`no_gold_reads`).
- **Zero rows.** A gold query whose every comparison had zero rows on both
  sides gets a NOT PROVEN line, and every V1/V2 check that compared no row is
  listed (strata named `empty` on their own list).
- **Copied generated text.** A gold SQL file that names the output schema,
  names a generated relation or contains a generated measure filter clause
  verbatim counts as generated, and a NOT PROVEN line says what matched. A
  data rule view is reported as the one item `relation:v_rule_*`, never as the
  text that matched, and case folds in ASCII only.
- **The report shows it.** With a verify result, `report.json` gains an
  `evidence` key, `report.md` an `## Evidence` section and the console
  `  EVIDENCE  ` lines: checks by kind, the mutant split, facets without
  authored evidence, zero-row comparisons and gold SQL with generated text.
  report reads verify's `evidence` object only when its values are of their
  closed sets and plain ids and its mutant split follows from the V4 checks of
  the same result; otherwise it shows "observation not recorded".
- **Opt-in require mode.** `[verify] gold_observation = "require"` makes a
  generated-only or unattributed kill fail (or `not_run` when suite items were
  left out), adds one `gold_evidence:<element>` check per measure, hierarchy
  and `ontology.class_column` on full-scope runs, and turns a passing
  `v1:<gold>` of a gold query that compared no row into `not_run`
  (`no_rows_compared`). It only ever turns a pass into a fail or `not_run`.
  `[verify] accepted_gaps` names known gaps and known generated-only kills.

See [design, "Evidence kinds"](../design.md#evidence-kinds), the
[report evidence](../contract-report.md#evidence-kinds-in-the-report), the
[configuration reference](../../skills/semantic-crosscheck/references/config.md)
and the [changelog](../../CHANGELOG.md).

## Compatibility and migration

- Engine code changed, so the engine fingerprint changed: `report` treats every
  result recorded by v0.22.1 as stale (`inputs_changed`). Rerun the whole
  pipeline after upgrading.
- No configuration needs editing, unless an identifier or a Cube member ends
  with a line break: that is now exit 2 (`invalid identifier: ...`, `bad Cube
  member ...`). In the default mode (`gold_observation = "disclose"`) no
  status changes, with one exception: a configuration whose gold SQL contains
  generated text now runs that gold query's items after the authored ones in
  V4, so its `killed_by` and V4 statuses can change (another item can fail
  first, or an item error or the item budget can be met first). This goes
  either way: `error` or `not_run` can become `pass`, and `pass` can become
  `error` or `not_run`.
- verify prints more NOT PROVEN lines for most configurations; scripts that
  count them see more (the clean demo's verify prints 8 instead of 4). report's
  console prints no new NOT PROVEN line of its own, but `report.md`
  "## Not proven" and the not_proven count of the `stage:verify` detail
  include verify's new lines. Console parsers should ignore lines that start
  with `  EVIDENCE  `.
- The two new `[verify]` keys are part of the configuration hash, so changing
  them makes earlier results stale.
- Build, reason and cube outputs, check ids, and reports without a verify
  result are unchanged apart from the engine fingerprint; the compatibility
  goldens hold this. `verify/mutation-coverage.json` keeps `schema_version` 1
  and only gains keys.
- No new runtime dependency: `requirements/` and the Cube adapter are
  unchanged.

## Known limitations

- **Authored is not correct.** Gold SQL wrong in the same way as
  `crosscheck.toml` (both from one misread specification) still agrees with
  the model and counts as authored.
- **Verbatim text only.** Paraphrased copies of generated SQL, generated SQL
  read through a view the user made, and dynamic SQL are not detected. A
  source table or CTE named like a generated relation is flagged; that only
  lowers a kind.
- **First detecting item only.** The suite stops at the first item that does
  not pass, so `detection` names that item's kind only, and it is exact for the
  replayed bindings (V1's first binding, the first `verify.mutant_bindings` per
  stratum) only.
- **Facets are not every dimension.** Facets cover measures, hierarchies, the
  joins of the generated model and the class column; other entity dimensions
  are not named. Facets without an operator (`max_depth`, `pairs`, the
  ancestor cube, node joins, the class column) can be compared but never
  detected.
- **Compared is not detected.** A facet compared with rows that hold values
  can still hide a wrong value that equals the right one on the sampled rows.
  Only an authored mutant kill shows that a change was seen.
- **Other vacuous passes.** `shacl:<id>` with no keys, `v5:closure:<h>` with no
  pairs and an unfiltered V3 pair test over zero keys are not disclosed.
- **No recomputation of measures.** Independent recomputation exists only for
  the closure; a measure's only non-generated evidence is gold SQL.
- **Require mode discloses dropped operators, it cannot stop them.** Operators
  left out of `verify.mutation_operators` are named in a NOT PROVEN line and in
  every `gold_evidence:<element>` detail.
- **Outside report.** `expect`, `data-rules` and the diagnostics stay outside
  report authority, and the closure oracle is not replayed against mutants.
- **Clean-demo numbers.** The counts of the clean demo come from one CI
  integration run of the implementation branch: checks by kind authored 17
  (2 of them compared no row), recomputed 1, generated 26, structural 40,
  mutation 12, all passing; mutants 9 killed with an authored detection, 3 by
  generated checks only, 2 equivalent on this data; facets 15 of 17 compared,
  1 detected, `part+m_firm_open` without authored evidence; zero-row checks
  `v2:q02_where_used:top` and, in the stratum named `empty`,
  `v2:q01_explosion:empty`; 18 NOT PROVEN lines in the quick start (8 of them
  from verify). With `verify.gold_observation = "require"` the clean demo's
  verify fails: the three generated-only kills and
  `gold_evidence:measures.firm_open` fail, the other five `gold_evidence`
  checks pass. The release step's own runs are the evidence for this release.
- Existing SQL, OWL, SHACL and synthetic-search limits remain, and no common
  Gold/Cube MVCC snapshot is created.
