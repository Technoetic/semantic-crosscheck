# semantic-crosscheck v0.2.0

Release date: 2026-10-16. A minor release adding synthetic SQL counterexamples and data-version evidence.

## What it is

semantic-crosscheck checks agreement between PostgreSQL 17, generated SQL and SHACL rules, OWL
reasoning with HermiT, Cube and hand-written gold SQL. This release adds a separate synthetic SQL
comparison command and optional data-revision binding to the existing pipeline. The configuration
format remains version 1; existing configurations need no new setting.

## Highlights

- **Actual SQL counterexamples.** Two trusted SQL files run over the same generated `part`,
  `bom_line`, `sales_order` and `stock` CTEs in a PostgreSQL read-only, repeatable-read transaction.
  Generated values are bound parameters. Deterministic NULL, duplicate-join, BOM-diamond and date-boundary
  scenarios expose successful disagreements in exact row multisets and projection names.
- **Bounded shrinking and replay.** A row deletion is accepted only when both queries execute and
  remain unequal. The reducer reports deletion 1-minimality, exhausted budgets and invalid trials;
  it never claims a global minimum. A separate synthetic `fixture.json` contains generated rows and
  SQL digests. Results and console output retain counts, identifiers and hashes, never query-answer rows.
- **Explicit limits on conclusions.** A found mismatch is `fail`/exit 1. Agreement within the search
  budget is `not_run`/exit 1, not an equivalence proof. Query failures and timeouts are errors, not
  counterexamples. This tool detects disagreement between the supplied SQL files; it does not establish
  which query expresses the intended business rule.
- **Optional data-revision binding.** Configure `source.data_revision_sql_file` with a trusted query
  returning exactly one nonempty text revision. Start/end probes on source and Cube endpoint roles
  must agree. Missing, changed or unreadable bindings cannot certify current evidence. Only hashes
  are retained; unconfigured data freshness is explicitly unbound.
- **Engine and query fingerprints.** Harness/CLI code, adapter inputs, selected Python runtime and
  dependency metadata, and the revision-query file participate in evidence freshness. These hashes
  do not identify the installed PostgreSQL, Java or Node.js runtime binaries or versions.
- **Forty-nine new tests**, including real PostgreSQL search, shrinking, replay, write rejection,
  revision changes, scalar validation, redaction and CLI dispatch. The suite now contains **562 tests**.

## Install

Claude Code (type these yourself, then restart Claude Code):

```text
/plugin marketplace add Technoetic/semantic-crosscheck
/plugin install semantic-crosscheck@semantic-crosscheck
```

Codex:

```text
codex plugin marketplace add Technoetic/semantic-crosscheck --ref v0.2.0
codex plugin add semantic-crosscheck@semantic-crosscheck-local
```

Follow the README setup instructions. Python 3.11 or later and PostgreSQL 17 remain required for the
database stages; HermiT needs Java 11 or later, and Cube needs Node.js 22 or later. Cube remains pinned
at 1.8.3 and the dependency lockfile is unchanged. No new runtime dependency is introduced.

After upgrading, rerun the relevant pipeline stages before relying on `report`: missing or changed
engine fingerprints invalidate older evidence. Without a revision probe, normal check verdicts remain
compatible and data freshness remains unproven.

Use the [counterexample reference](../../skills/semantic-crosscheck/references/counterexamples.md)
for the synthetic examples, exact schema, budgets and replay command. Replay requires the same SQL
files and the saved scenario and seed; a changed SQL digest or non-generated fixture row is rejected.

## Known limitations

- Search is bounded to four synthetic scenario families. It does not discover every input, SQL defect
  or business-rule error. Row-deletion minimality is not global minimality or value minimization.
- SQL files and revision probes are trusted code. Although generated relations shadow the fixed CTE
  names and sessions are read-only, SQL may explicitly reference real database objects. Use a dedicated
  test database; this is not a SQL sandbox or proof of source-independent execution.
- The operator must update a never-reused revision atomically with every relevant source change.
  Boundary probes do not create a shared MVCC snapshot across sessions, and cannot detect omitted or
  reused revisions. Hashing a token does not prove the owner's revision discipline.
- The engine fingerprint has the bounded scope described above; it is not a complete environment or
  dependency-binary attestation. Revisions and source stability still need operational discipline.
- Existing query, SHACL/OWL and platform limits remain: supported OWL/SQL definitions only, SQL-only
  shapes reported as unproven, one swept parameter per gold query, the documented date-range forms,
  a 50,000-row Cube response limit and one Cube process per mutant.
- Local optional-engine skips remain explicit. Public CI must supply the PostgreSQL, Java and Cube
  components and run the tests without skips before it can establish full-stack success.
