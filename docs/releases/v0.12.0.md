# semantic-crosscheck v0.12.0

Release date: 2026-10-28. A minor release adding three authored boundary fixtures and an opt-in, two-arm
constraint sensitivity diagnostic. Existing defaults and dependency pins are unchanged.

## What it is

semantic-crosscheck generates PostgreSQL hierarchy closures, SQL and SHACL rules, OWL/HermiT reasoning
and a Cube semantic layer from one configuration, then compares their results and hand-written gold SQL.
This release adds fixture-bound evidence for three stock-query boundaries and a bounded way to compare trusted
SQL under declared constraints and explicitly relaxed constraints. Neither addition proves SQL equivalence or
changes operational V1-V5 or the pipeline report verdict.

## Highlights

- **Authored boundary examples.** `examples/expect-boundaries/` contains three SHA-bound `authored` cases with
  independently written SQL, configuration and hand-calculated expected rows: a parent with no stock retains
  raw NULL; a parent whose stock is filtered out uses explicit zero normalization; and the same label in two
  regions retains the composite `(region, label)` result key. The existing NULL-grain policy excludes stock
  whose part key is NULL. Temporary-copy sensitivity tests exercise wrong authored rows, a shared wrong filter
  and label-only grouping. Runtime errors remain errors. See the
  [fixture specification](../../examples/expect-boundaries/fixture-spec.md).
- **Opt-in constraint audit.** `counterexample --constraint-audit FILE` runs one SQL pair in two finite domains.
  The declared arm enforces the original constraint profile. The relaxed arm removes selected source
  declarations and accepts a witness only outside the full original profile. PostgreSQL disagreement under the
  existing typed bag comparison is required; solver satisfiability alone is never a witness.
- **Explicit manifest and projected domain.** A strict version 1 manifest binds the exact original constraint
  bytes, every source declaration's provenance category and explicit relaxation selectors. Provenance categories
  are caller claims (`catalog`, `human`, `observed`, `inferred`), not independently verified facts. Projection
  reuses the existing constraint loader, rejects missing retained FK targets and zero normalized rule deltas,
  and does not automatically cascade dependent declarations.
- **Separate audit replay.** The versioned `sxc-synthetic-constraint-audit` format binds exact SQL, specification,
  original and projected profiles, manifest, arm classification and budgets. Replay rechecks one arm and labels
  the other `not_replayed`. Ordinary counterexample replay formats remain unchanged and reject audit files.
  Version 1 supports `rows` shrinking only, preserving finite values, types and original minimum/maximum row
  bounds during reduction and replay. Each witness is reconfirmed after reduction and after both searches,
  and exact input hashes are revalidated before atomic publication.

## What the evidence shows

| Outcome | Meaning |
|---|---|
| Declared-domain PostgreSQL disagreement | `fail`: the two queries disagree on a confirmed finite fixture satisfying the declared profile. |
| Relaxed, outside-declared-domain disagreement | Diagnostic `not_run`: a confirmed fixture disagrees outside the full original profile. It does not establish a false constraint or an actual production defect. |
| Bounded no-witness or incomplete search | `not_run`: no equivalence, correctness or exhaustive disappearance claim, including finite `space_exhausted` or `unsatisfiable` outcomes. |
| Query, reduction or confirmation exception | `error`, never an accepted witness. |
| Boundary expect pass | Agreement with the authored rows on this pinned synthetic fixture, separate from operational V1-V5. |

No audit outcome is `pass`. Error dominates fail; declared fail dominates diagnostic `not_run`.
Found/not-found outcomes of different bounded prefixes do not prove causal necessity for a selected relaxation.

## Compatibility and migration

The audit is used only when `--constraint-audit FILE` is supplied. Ordinary searches, constraint JSON, replay
formats, pipeline defaults and dependency pins are unchanged. It uses the existing optional solver dependency
in `requirements/witness.txt`; no new dependency is added. The authored examples use the existing expect format
and node/measure link with PostgreSQL 17+ and Cube 1.8.3.

The audit also requires `--witness-schema`, `--constraints`, `--reference-sql` and `--candidate-sql`.
Explicit `--scenario`, mutation/gold/metamorphic modes and `--shrink-strategy structured` are rejected before
connection. See the [audit contract and synthetic COUNT example](../constraint-audit.md).

Rerun `build`, `reason`, `cube`, `verify` and `report` after upgrading because the engine fingerprint changes.
Installing the release neither reruns stages nor certifies old evidence.

## Known limitations

- The authored corpus covers only these three synthetic row cases, exact numeric aggregates, the existing
  node/measure link, literal NULL, explicit zero normalization and composite result keys. It is inspired by
  SLayer's boundary ideas, with no upstream data, SQL, runner, comparator or expected rows copied. It does not
  port the upstream feature corpus or assert that its DuckDB/Cube outcomes equal PostgreSQL/Cube outcomes.
- Generic multi-hop entity joins, rolling windows, time spines, multi-stage/derived measures and
  expected-error-as-pass probes are outside the authored corpus. An expect pass is not production coverage.
- Audit manifests contain caller-claimed provenance. No catalog is automatically inspected; no category
  validates a constraint or selects a relaxation. A nonzero normalized rule delta is not a proof that the
  finite reachable domain changes or that the removed contribution caused the disagreement.
- Search/example, solver and shrink budgets apply per arm. Total work can approach twice a single search
  plus final confirmations. The finite solver has fixed model ordering; recording a seed does not change it.
  Different arms can enumerate different bounded prefixes.
- Audit v1 supports row-deletion shrinking only and preserves original minimum/maximum row bounds. It cannot
  widen finite values, types or row bounds, and provides no structured reduction trace or equivalence engine.
- Each evaluated fixture uses a read-only REPEATABLE READ transaction, but fixtures and arms share no whole-run
  snapshot. Supplied SQL is trusted and can explicitly read external relations; synthetic CTEs are not a SQL
  sandbox. Run only in a dedicated synthetic database. Result summaries contain counts/IDs/hashes, while local
  replay artifacts may contain synthetic rows. Hash bindings are not authenticity signatures or proof of solver
  origin.
- Existing [v0.11.0 limitations](v0.11.0.md#known-limitations) still apply.
