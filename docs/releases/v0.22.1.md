# semantic-crosscheck v0.22.1

Release date: 2026-11-11.

## What it is

semantic-crosscheck compares PostgreSQL, SHACL, OWL/HermiT and Cube with
independently authored Gold SQL. This is a documentation and unit-test
release. It corrects places where the README, the command documents and the
plugin descriptions had drifted from the code, and it adds 14 unit tests: eight
hold those documents against the code, six hold fail-closed rules.

No stage, check, option, result format, configuration key or dependency
changes. The only product-code change is the version constant. A configuration
that worked with v0.22.0 produces the same checks and verdicts; the engine
fingerprint differs, so the operational stages have to be rerun once after
upgrading (see Compatibility and migration).

## Highlights

- **The README opens with what the tool is and who it is for.** The title, the

  that preceded the title are in a "Recent changes" section near the end,
  their text unchanged. `SKILL.md` starts with the core description; its four
  release notes are under "Optional offline diagnostics", unchanged.
- **Corrected statements.** The clean demo prints 14 `NOT PROVEN` lines (the
  README said 13), and the breakdown accounts for all of them. All 21 slash
  commands are listed and linked to their command documents (the list had
  eight). `SXC_DEBUG` is documented for the stages that read it (the tables
  said every stage); the diagnostic stages,
  `counterexample --constraint-audit` and `expect` with `spec_source` cases
  print a fixed reason code only. Unit tests need `requirements/core.txt` and
  `requirements/witness.txt` (CONTRIBUTING named `reason.txt` only). The
  "결과 읽기" and "검증 한계" anchors sit above their own headings.
- **What agreement shows.** One README paragraph says what agreement between
  the generated layers shows, what the independent evidence is (hand-written
  gold SQL, authored expected rows, the independent closure recomputation) and
  that existing Cube models, ontologies and SHACL files are not inputs. The
  marketplace entry and the Codex short description say "check" where they
  said "prove"; the Codex long description starts with what the tool is and
  what a pass means.
- **Reading a failed run.** The README section "실패한 실행 읽기" shows a
  failing build and report, taken from the compatibility goldens, and how to
  read each part of the output.
- **Examples that resolve from a project folder.** `commands/xc-grain.md`,
  `commands/xc-shacl-repair.md`, `commands/xc-expect.md` and
  `references/codex.md` name example files from the plugin root; the grain
  example writes its result to `.sxc-grain` in the working directory.
- **Release archive command.** The README gives the `git archive` command
  that makes the release ZIP from the tag, and under it a dated record of the
  comparison with the published v0.22.0 asset.
- **Fourteen unit tests.** Eight docs and packaging tests pin the corrections
  above: the command list against `commands/`, the wording of the manifest
  and command descriptions, example paths from the plugin root, anchors above
  their headings, the `NOT PROVEN` counts in the prose, the failing example
  against the goldens, the version in the archive command and the dated
  record under it. Six unit tests pin fail-closed rules: a result or a stage
  without any check is `not_run` (exit 1); a relative `PATH` entry is never
  searched for node, npm or java; an entity table outside `source.schemas` is
  a configuration error; in verify a gold query without any binding is
  `not_run` (`no_binding`), and an empty stratum passes only with a
  `not_proven` line. None of them needs a database.

The full list is in the [changelog](../../CHANGELOG.md).

## Compatibility and migration

- Outside documentation, plugin manifests and tests, the only file that
  differs from v0.22.0 is `semantic_crosscheck/__init__.py`, and there only
  the version constant. `sxc.py --version` prints it, and `cube-install`
  sends it as the User-Agent of its download.
- No new runtime dependency: `requirements/` and the Cube adapter are
  unchanged.
- The file that holds the version constant is one of the files the engine
  fingerprint hashes, so the fingerprint changes. `report` treats results
  recorded by v0.22.0 as stale (`inputs_changed`): rerun the operational
  stages after upgrading. Because no other engine code changed, they produce
  the same checks and verdicts as v0.22.0 for the same configuration and data.
- No configuration needs editing.

## Known limitations

- **Nothing is lifted.** This release changes no engine behaviour, so every
  known limitation of [v0.22.0](v0.22.0.md) applies unchanged.
- **Equal results follow from equal code.** That a configuration gives the
  same checks and verdicts as with v0.22.0 rests on the engine code being
  unchanged apart from the version constant. It was not measured again
  against a database for this release.
- **What the new tests cover.** Each new test pins the rule or the passage it
  names. The test of the descriptions refuses "prove", "guarantee" and an
  unnegated "proof" or "proven"; it does not cover every word that can
  overstate a check. "certify" passes: the data-rules help text uses it for
  comparing the lookup views with the agreed rows, and the descriptions that
  use it follow the help text.
- **Windows-only local run.** The new `PATH` test expects `node.cmd` on
  Windows and `node` elsewhere; the second branch was not executed locally.
- **The archive record is about v0.22.0.** The dated record under the
  `git archive` command in the README compares that command's result with the
  published v0.22.0 asset. It says nothing about this release's archive, whose
  comparison is part of the release step.
