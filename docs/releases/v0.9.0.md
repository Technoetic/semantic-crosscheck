# semantic-crosscheck v0.9.0

Release date: 2026-10-24. A minor release adding a literal expected-row oracle for mistakes that the gold
SQL and the configuration share, chunked V3 pair comparison of every key within a budget, and a W3C SHACL
core subset for the SHACL engines. Existing configurations and default stage behavior remain supported. The
new results do not promote operational V1–V5 coverage.

## What it is

semantic-crosscheck generates PostgreSQL hierarchy closures, SQL and SHACL data rules, OWL/HermiT
reasoning and a Cube semantic layer from one configuration, then compares results with each other
and with hand-written gold SQL. When the gold SQL and the configuration share one mistake they agree,
so this release adds rows a person writes from the business specification as a third oracle, run on a
small fixture database the user loads. Separate synthetic commands still test generated fixtures in
dedicated test environments.

## Highlights

- **Literal expected rows.** `[[gold.expect]]` cases on a `[[gold]]` entry hold the expected output rows
  of the gold query for a small fixture: `source = "authored"` with a `spec` location (the only
  independent evidence) or `"captured"` (regression evidence only), `params`, `rows` with
  `{ null = true }` for NULL, `partial` and an optional `fixture_sha256` pin. The new `expect` stage reads
  the operational configuration but runs build, cube, the gold SQL and Cube only on a dedicated fixture
  database the user has loaded (`--dsn-env`, default `SXC_EXPECT_DSN`, with explicit
  `--allow-fixture-database`); it never runs fixture SQL and never connects to an operational DSN.
  `expect:<gold>[<i>]` passes only when both sides equal the expected rows. Agreeing sides that differ
  from them fail as `common_mode` (authored) or `regression` (captured); a disagreement fails as
  `gold_mismatch`, `cube_mismatch` or `both_mismatch`. `expect:fixture` compares digests of the fixture
  taken before the build and around the cases, and a change turns every pass into `not_run`. The result is
  reported separately: `report` does not read it. See [xc-expect](../../commands/xc-expect.md) and
  `examples/expect/`.
- **Chunked V3 pair comparison.** `verify.pair_key_budget` (default 2000, at least the 2,000-key cap) lets
  a pair test with more keys than the cap compare every key in the baseline run. The key count and every
  non-NULL key are read in md5 order in one REPEATABLE READ snapshot and compared in consecutive chunks of
  2,000 keys through the existing filtered queries, plus the NULL key group through a `notSet` filter.
  A mismatch in any chunk fails the test, a query error makes it an error, and keys missing from Cube's
  together answers make it `not_run` (`keys_not_answered`): only keys Cube answered count as compared.
  Above the budget the deterministic sample and its d95 bound stay.
- **W3C SHACL core subset.** `shacl-corpus --w3c-suite [DIR]` (or `SXC_W3C_SHACL_SUITE` with a bare
  `--w3c-suite`) compares pySHACL and Apache Jena with the expected reports of the W3C SHACL core test
  suite, pinned at w3c/data-shapes `1dfcd9f` by a digest over the files read. Only approved `sht:Validate`
  entries inside the sxc profile run (the components and severities sxc's exporter emits); every other
  entry is `not_run` with a reason id. Check ids are `w3c:<engine>:<case>`. On the pinned suite both
  engines matched all 6 in-profile cases (pySHACL 0.40.1 and Apache Jena 6.2.0). The CI integration job
  fetches the pinned tarball, verifies its SHA-256 and content digest, and runs the subset; the suite is
  read at test time and never vendored.

## Compatibility and migration

Existing configurations, default commands and dependency pins remain supported, and no default changes
what a stage compares. Two keys are new and optional: `verify.pair_key_budget` (the default 2000 keeps the
previous sampled comparison) and `[[gold.expect]]` (only the `expect` stage runs the cases; every stage
validates them, and adding or editing one changes `crosscheck.toml`, so `report` treats earlier operational
results as stale until they are rerun). The not proven line of a sampled V3 pair test now also says that
the NULL key group is not compared; statuses are unchanged. `SXC_EXPECT_DSN` is read only by the new
`expect` stage and `SXC_W3C_SHACL_SUITE` only by a bare `--w3c-suite`. See the [configuration reference](../../skills/semantic-crosscheck/references/config.md)
and the [README](../../README.md).

Rerun `build`, `reason`, `cube`, `verify` and `report` after upgrading: the engine fingerprint changes and
previous stage results become stale. Installing an upgrade does not certify older results or rerun stages
automatically.

## Install

Claude Code:

```text
/plugin marketplace add Technoetic/semantic-crosscheck
/plugin install semantic-crosscheck@semantic-crosscheck
```

Codex:

```text
codex plugin marketplace add Technoetic/semantic-crosscheck --ref v0.9.0
codex plugin add semantic-crosscheck@semantic-crosscheck-local
```

Install the required Python packages from the actual plugin root and run `doctor`. The `expect` stage
needs no new package. Only the optional SHACL corpus command needs the separately configured Jena
distribution, and its W3C mode a separately downloaded w3c/data-shapes checkout.

## Known limitations

**Sampled pair tests do not count answered keys.** The chunked path refuses keys missing from Cube's
together answers, but the sampled path does not check them yet. That path covers every pair test above the
budget (by default, above 2,000 keys) and every V4 replay. A sample key that Cube leaves out of the
together answer is never compared, while the not proven line still counts it as compared and the d95 bound
is computed from the keys requested. This predates 0.9.0 and is planned as a follow-up. A sample also never
compares the NULL key group, which its not proven line now says.

**Chunked pair tests** read every key up to the budget in one statement under
`source.statement_timeout_ms` and hold them in memory. The key set comes from one snapshot, but each Cube
query reads its own, shared with no other query and not with SQL.

**The expect DSN guard** compares the fixture DSN only with the operational DSN variables set in this
environment, by value and by host, port and database. Another name for the same server is not detected
and an unset variable is not compared, so the fixture must be a dedicated database. A case covers only
its fixture rows and parameters, not operational data; authored rows are independent only as far as they
follow the cited specification, and captured rows only show that nothing changed since the capture. The
digests show the fixture equal at the points they are taken, not one shared snapshot, and the gold SQL and
Cube read it in separate sessions. SHARE locks are held only when the role can take them. A
`fixture_sha256` pin depends on the source tables' rows and column types (and on the database encoding for
text outside ASCII), not on the default collation or session settings. The digest is not salted, so a
result can confirm guessed fixture rows: keep the fixture synthetic.

**The W3C mode checks the engines only.** It validates the suite's own shapes and data graphs, so it does
not exercise sxc's exporter: run it together with the fixed corpus. On the pinned suite 92 of 98 entries
are outside the profile and `not_run`, so the W3C mode never passes as a whole; an unpinned suite runs no
engine unless `--allow-unpinned-suite`, and then `w3c:suite` keeps the stage from passing. No in-profile
W3C case uses `sh:minInclusive`, so that bound is checked only by the fixed corpus.

No real-data V1–V5 promotion, universal correctness proof, shared cross-stage snapshot or runtime
attestation is claimed. The existing [v0.8.0 limitations](v0.8.0.md#known-limitations) still apply.
