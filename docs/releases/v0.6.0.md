# semantic-crosscheck v0.6.0

Release date: 2026-10-20. A minor release that turns two documented gaps into real comparisons — report-mode
cycles in the independent closure oracle and shapes that combine `class` with bounds in SHACL — and adds a
bounded-exhaustive BOM scenario for the metamorphic mode. The configuration format remains version 1.

## What it is

semantic-crosscheck generates PostgreSQL closures, SQL/SHACL rules, OWL/HermiT and Cube models from
one configuration and compares them with each other and hand-written gold SQL. This release widens what
the independent checks cover: closures built with `on_cycle = "report"`, shapes that combine `class` with
bounds, and every small acyclic BOM in a stated scope. Each result still states its scope; a successful
synthetic check does not replace verification on real data.

## Highlights

- **Report-mode cycles in the independent closure oracle.** `v3:closure_oracle:<h>` no longer reports
  `on_cycle = "report"` hierarchies as `not_run`. An iterative Tarjan search, charged to the operation
  budget, finds the strongly connected components of the logical edge graph. Every logical edge inside one
  (self-loops included) is removed — the same rule the builder applies — and the rest is folded exactly.
  `dropped_cycle_edges` and `cycle_nodes` are recorded for information, and a pass that removed edges is
  listed in `not_proven`. A cycle left after removal would be an internal defect and is reported as `error`
  (`scc_removal_left_cycle`).
- **SHACL comparison of class-and-bounds shapes.** A shape that combines `class` with bounds now has two
  property shapes in `build/shapes.ttl`: `sh:class` on the column predicate, and the bounds on a new value
  predicate `<entity>.<column>/value` that carries the same column value as a literal. A row flagged by
  either property shape counts for the shape, matching its SQL view. Only `sql_violation` shapes remain
  checked in SQL alone.
- **Bounded-exhaustive BOM fixtures.** `counterexample --metamorphic-sql FILE --scenario bom_exhaustive`
  runs every connected acyclic BOM with 2-4 parts, 1-5 `bom_line` rows, at most 2 rows per (parent, child)
  pair and `qty_per` in {1, 2} — 1,743 isomorphism classes under two label placements, 3,486 cases — and
  compares each answer exactly with the independent closure oracle (`counterexample:metamorphic:oracle`).
  A `UNION` closure fails deterministically at case 4, while with seed 7 the seeded `bom_diamond` run sees it
  in only 6 of its 64 default cases. The method follows Marinov et al. (2003): every input within a small
  scope, one representative per isomorphism class.

## Compatibility and migration

Existing version 1 configurations need no change. No runtime dependency is added. Python requirements,
the Cube 1.8.3 pin and the dependency lockfile are unchanged.

Rerun the whole pipeline after upgrading, build first, then reason, cube and verify: the engine fingerprint
is an input of all four data stages, so earlier results are reported stale (`inputs_changed`), and
`build/shapes.ttl` changes for configurations with class-and-bounds shapes. The new report-mode
comparison runs in `verify`.

Behaviour changes to read before upgrading:

- Report-mode hierarchies whose oracle check was `not_run` are now compared and can fail. A configuration
  that passed with that check `not_run` can therefore require attention.
- Class-and-bounds shapes are now exported to SHACL. Their target and class-entity rows count against
  `verify.shacl_max_rows`, and next to a bound-only shape on the same column (or a class shape naming another
  entity) an extra value group is opened that exports its target rows again. If the total exceeds the limit,
  every `shacl:<id>` check is `not_run` (`resource_limit`): check the reported row count after upgrading or
  raise `verify.shacl_max_rows`.
- `--scenario bom_exhaustive` is accepted only with `--metamorphic-sql`, and `--max-examples` must be omitted
  or at least 3,486. It passes only when every admissible case was compared. No check passes partially:
  at the first failure and in a one-case replay the failed checks fail and the others are `not_run`; a
  resource bound in an original answer makes every check `not_run`.
- The configuration still accepts only `error` and `report` for `on_cycle`. Called directly, the oracle
  answers any other value with `not_run` (`unsupported_on_cycle`), whatever the graph.

## Known limitations

The report-mode oracle reproduces the builder's rule: a logical edge is removed when its parent and child
share a strongly connected component. Paths through removed edges are left out of the closure by policy;
a passing check states the number of removed edges in `not_proven`. The oracle's endpoint-type, depth and
resource bounds are unchanged.

Class-and-bounds comparison reads the bounds from the value predicate; a NULL column value writes neither
triple, as before. Because these shapes are now exported, a large configuration can reach
`verify.shacl_max_rows`.

`bom_exhaustive` tests only its stated scope: at most 4 parts, 5 lines, 2 lines per pair, `qty_per` in
{1, 2} and the two label placements. Larger topologies, other quantities and other label orders are not
tested, and the oracle compares `qty` only. Synthetic fixtures do not establish correctness on real data.

Existing limits remain: V3 additivity covers `ontology.class_column`; sampled pair-test detection bounds
depend on independence from the fixed md5 ordering; `sql_violation` shapes are SQL-only; the v0.5.0 limits
of the closure oracle's supported key types, of operator-directed fixtures and of OWL witnesses are unchanged
(see the [v0.5.0 notes](v0.5.0.md#known-limitations)). No shared MVCC
snapshot across stages, universal SQL equivalence or runtime attestation is claimed. Data-revision binding
still depends on the source owner's atomic, never-reused revision contract.
