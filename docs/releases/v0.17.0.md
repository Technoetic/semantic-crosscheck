# semantic-crosscheck v0.17.0

Release date: 2026-11-03. This release hardens V3 response-member validation,
the known-volatile SQL call gate, and current-data witnesses for undated
aggregate mutations. Dependency pins, default pipeline stages and report
authority remain unchanged.

## What it is

semantic-crosscheck generates PostgreSQL hierarchy closures, SQL/SHACL rules,
OWL/HermiT reasoning and a Cube semantic layer, then cross-checks them against
each other and independently authored gold SQL. These fixes distinguish an
incomplete adapter answer from a valid NULL, reject quoted forms of known
unstable calls, and avoid classifying observable aggregate changes as equivalent.

## Highlights

- **Requested V3 members must exist.** Every returned row must contain each
  requested dimension and measure before canonicalization, across totals,
  additive groups, pairs, chunks, NULL groups and V4 replays. A present NULL
  remains valid. A missing member is an invalid response; an error in a V4
  replay follows the existing retry/error path, rather than counting as a kill.
- **Quoted volatile calls are checked.** Known unstable calls such as
  `"random"()` and schema-qualified variants are recognized in the supported
  SQL inputs. Lexical clause/delimiter context keeps valid quoted relation
  aliases, column lists and string literals distinct from calls. Regression
  controls include ONLY, adjacent AS, NOT, qualified OPERATOR, VALUES and
  ROWS FROM boundaries. This is a bounded lexical gate over trusted SQL, not a
  PostgreSQL parser or a custom-function volatility sandbox.
- **Undated witnesses compare generated outputs.** Filter-drop and
  normalization-drop witnesses compare the original and mutated generated
  key/value bags with bidirectional `EXCEPT ALL`. This catches NULL-to-zero and
  missing-key differences while avoiding source-row-count false positives from
  cancellation or non-extremal MIN/MAX additions. Counts describe differing
  output rows from both directions, not changed source rows. The existing dated
  witness path is unchanged. See [mutation coverage](../mutation-coverage.md).

## Compatibility and migration

An incomplete Cube response that previously passed V3 can now produce
`invalid_response`; repair the adapter answer instead of filling missing keys
with NULL or zero. V4 cannot treat that adapter error as a detected mutant.

Current-data mutation classifications may change. An observable undated change
must be served to the suite; a mutation whose generated outputs do not change
can be classified as equivalent on the current data. This does not prove
equivalence for other data revisions or unsupported models. Raising a budget
does not remove that boundary.

Rerun operational stages after upgrading: the engine fingerprint changes with
the package. Installing this release neither reruns stages nor refreshes evidence.

from the release. Verify both listed SHA-256 values before unpacking. The ZIP

attestation. Fresh downloaded bytes are also compared with the expected checksums
and tracked Git inventory.

## Known limitations

- V3 validates the requested response contract; it cannot detect a shared error
  in both an independently supplied expectation and the model.
- The SQL gate recognizes known unstable calls within the supported syntax.
  It does not discover arbitrary user-defined volatile functions or sandbox SQL.
- The undated witness observes current generated key/value outputs. It does
  not prove general SQL equivalence, future-data equivalence or complete semantic
  coverage. The dated path retains its existing behavior.
- Separately served Cube requests and witness SQL do not share a guaranteed MVCC
  snapshot. Concurrent source changes remain a limitation.
- Windows-local runtime and unit exclusions do not establish unexecuted engine
  or platform behavior. Public CI records its own actual results.
- Existing [v0.16.0 limitations](v0.16.0.md#known-limitations) continue to apply.
