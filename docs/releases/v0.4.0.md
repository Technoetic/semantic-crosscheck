# semantic-crosscheck v0.4.0

Release date: 2026-10-18. A minor release that tightens several checks, adds an opt-in gold-independent
oracle for BOM closure SQL and pins the Cube SQL planner. The configuration format remains version 1.

## What it is

semantic-crosscheck generates PostgreSQL closures, SQL/SHACL rules, OWL/HermiT and Cube models from
one configuration and compares them with each other and hand-written gold SQL. This release closes
gaps that the 0.3.0 limitations listed: SQL reads of one check now share one snapshot, sampled
comparisons state what they can detect, additivity covers many-to-one joins, SHACL compares shapes
that were previously skipped, and a closure SQL can be checked without a gold query.

## Highlights

- **One snapshot per check.** `db.read_only(..., isolation="repeatable read")` runs the statements a
  check combines in one READ ONLY REPEATABLE READ transaction: the V3 pair-test key count and key
  sample, and the catalog reads the cube stage builds its model from. Single-statement reads keep
  READ COMMITTED. Cube sessions and stage boundaries still share no snapshot and rely on the
  data_revision contract.
- **Stated detection bound for sampled V3 pair tests.** Above 2,000 keys the detail gains `d95_keys`
  and `d95_rate`, the smallest number of mismatching keys a deterministic sample detects with 95%
  probability (zero-acceptance hypergeometric sampling, computed exactly), and not_proven says so.
  A V4 mutant that survives a suite replaying such a sample is marked `sample_blind_possible`.
- **Additivity over many-to-one joins.** V3 `additive` tests now cover every sum/count measure
  grouped by `ontology.class_column` on every cube Cube reaches through many_to_one / one_to_one
  steps only (the demo gains 4 checks: 42 to 46). Each test also compares Cube's NULL group with an
  independent SQL that follows the join direction (forward paths: anti-join; dimension-rooted paths:
  matched rows with a NULL class). Paths with a one_to_many step are listed as not applicable. The
  method follows [Aggregation Consistency Errors in Semantic Layers](https://arxiv.org/abs/2307.00417)
  (HILDA 2023).
- **Pinned Cube SQL planner.** The Cube child always gets `CUBEJS_TESSERACT_SQL_PLANNER=true`;
  inherited values are dropped. `cube:meta` records `cube_version` and `sql_planner` on every served
  run, and `report` treats a cube result recorded under another or no planner as stale. The Cube pin
  stays at 1.8.3.
- **BOM metamorphic relations.** `counterexample --metamorphic-sql FILE` checks one trusted closure
  SQL (columns ancestor, descendant, qty) on seeded bom_diamond fixtures against four relations with
  exact decimal arithmetic: diamond unfolding, scaling one multi-path line, adding a disjoint
  component and splitting a line through a unit node. A violation fails with exit 1 and a replayable
  `fixture.json`; vacuous relations are `not_run`. The principle follows EDC (PACMMOD 3(6), 2025); no
  code is borrowed.
- **SHACL value groups instead of `shared_path`.** Shapes whose column already carries another kind of
  RDF value are validated in extra data graphs (`extra:<n>`) of the same snapshot; everything else
  stays in one `main` graph exactly as in 0.3.0. One group's validation failure errors only that
  group's shapes.

## Compatibility and migration

Existing version 1 configurations need no change. Requirements, the Cube 1.8.3 pin and the dependency
lockfile are unchanged, and no runtime dependency is added.

Rerun the pipeline after upgrading. Every stage result records the engine fingerprint, so results
written by 0.3.0 are stale (`inputs_changed`), and a cube result without a recorded planner is stale
as well (`cube_runtime_missing`).

Behaviour changes to read before upgrading:

- A configuration with a column that needs two kinds of RDF value now exports that table once per
  value group. `verify.shacl_max_rows` limits the sum over the groups, so such a configuration near
  the limit can become `not_run` (`resource_limit`) where 0.3.0 skipped those shapes. Configurations
  without such a column export exactly what 0.3.0 exported.
- A `v3:additive` test passes only when the groups add up and the NULL groups agree; its detail gains
  `null_group_equal`, `null_group_rows` and `orphan_rows`.
- `counterexample` enforces `--reference-sql` and `--candidate-sql` in the stage (exit 2 with a
  result.json), chooses the default `--scenario` by mode, and refuses a blank trusted SQL file with
  exit 2.
- `shacl_check.export_graph` is replaced by `export_graphs` (one graph per value group).

```text
/plugin marketplace add Technoetic/semantic-crosscheck
/plugin install semantic-crosscheck@semantic-crosscheck
```

Codex:

```text
codex plugin marketplace add Technoetic/semantic-crosscheck --ref v0.4.0
codex plugin add semantic-crosscheck@semantic-crosscheck-local
```

remaining components. See the [README](../../README.md) for complete setup and update instructions.

## Known limitations

V3 additivity covers `ontology.class_column` only; other dimensions would need a group-count cap
against Cube's 50,000-row limit. The 95% bound assumes mismatching keys are independent of the fixed
md5 sample order. The recorded planner is the value the runner passes to Cube, not one read back
from Cube.

The metamorphic relations test only the given SQL on one bom_diamond topology with seeded
quantities. Errors that the transforms leave invariant (edge direction, a wrong quantity column,
filter mapping) are not detected, and a set-semantics (UNION) closure is caught only on cases with
equal-product paths. Passing relations upgrade no other check.

`class_and_bounds` shapes remain SQL-only. Trusted SQL can reference real objects explicitly;
synthetic CTEs are not a sandbox. No global minimum, universal SQL equivalence, shared MVCC snapshot
across Cube or stages, or runtime attestation is claimed. Data-revision binding still depends on the
source owner's atomic, never-reused revision contract.
