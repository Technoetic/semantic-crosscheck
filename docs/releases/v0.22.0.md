# semantic-crosscheck v0.22.0

Release date: 2026-11-09.

## What it is

semantic-crosscheck compares PostgreSQL, SHACL, OWL/HermiT and Cube with
independently authored Gold SQL. This release adds an optional `data-rules`
stage for structural data rules that are easy to state and tedious to check by
hand, such as "a kit used by another assembly needs components of its own" or
"a stored level equals the longest chain below the part". Every finding is
derived twice by independent means, and the keys a rule finds are read in the
database, never from results or console output.

## Highlights

- **Typed data rules, evaluated twice.** `[data_rules] file` names a closed
  TOML rule file with six kinds (`row`, `duplicate`, `mode_outlier`,
  `same_signature`, `stored_metric`, `text_quantity`), named sets and reference
  sets. The `data-rules` stage evaluates each rule on one READ ONLY REPEATABLE
  READ snapshot as compiled PostgreSQL with bound parameters and as an
  independent standard-library Python evaluation of the rows exported in the
  same transaction. A rule gets a verdict only when the canonical output
  multisets are equal (`rule_xcheck:<id>`); a disagreement leaves it `not_run`.
- **Authored examples.** `[[rule.example]]` holds small typed rows and the
  output written from the business rule. Both paths evaluate them without
  reading a table; `common_mode` (both paths agree, the authored rows differ)
  fails `rule_example:<id>` and leaves the rule `not_run`. Examples are
  required by default.
- **Certified lookup views.** With `views = true` (the default) build creates
  `v_rule_<id>` and `v_rules_subjects` in the output schema, and data-rules
  proves that they return exactly the agreed rows in canonical order
  (`rule_lookup:<id>`, `rule_subjects:lookup`). Query them in the database with
  the user; results hold counts and ids only, and `rules.sql` holds
  placeholders only.
- **Fail-closed gates.** Unsupported column types and nondeterministic
  collations, a non-UTF8 server, NULL or duplicate keys, NaN and infinities,
  NULL edge quantities, unbounded heights, long texts and the row budgets
  (`max_export_rows`, `max_rule_rows`) leave the rules they concern `not_run`,
  never passed.

See [data rules](../data-rules.md), the [command](../../commands/xc-data-rules.md)
and the [clean-room synthetic example](../../examples/data-rules/).

## Compatibility and migration

- Without `[data_rules]` nothing changes: generated SQL, `shapes.ttl`,
  `fk_review.sql`, check ids, next actions, results and `report.md` are
  byte-identical to v0.21.1. Goldens captured on v0.21.1, before any data-rules
  code existed, enforce this together with the unchanged README quick start.
- New engine modules change the engine fingerprint: rerun the operational
  stages after upgrading.
- No new runtime dependency. The Python evaluation uses the standard library
  only; the core, reason and Cube pins are unchanged. The shared modules other
  tools may vendor (`naming`, `result`, `canon`, `ident`, `db`, `constraints`)
  are byte-identical; only the package version changes.
- To opt in, add `[data_rules]` with a rule file whose examples are written
  from the business rules, run `build` (it creates the views) and then
  `data-rules`. The check role needs no new privilege: build creates the views
  in the output schema the role already owns, and data-rules only reads.
  report's required stages and verdict are unchanged; it adds one `not_proven`
  line when `[data_rules]` is configured and never reads the data-rules result.

## Known limitations

- **Common mode.** Both evaluations read the same rule file, so their
  agreement does not show that a rule or its constants are the right business
  rule. Authored examples pin only the cases they contain; a misunderstanding
  no example covers stays invisible. Every run with an agreed rule carries a
  `not_proven` line saying so.
- **Live views.** `v_rule_<id>` and `v_rules_subjects` equal the certified rows
  only at the time data-rules checked them; rerun it after the data changes.
- **Constants in view definitions.** Rule constants appear as literals in the
  view definitions and in `build/build.sql`, as `sql_violation` predicates do.
- **Regex capture assignment.** The pattern subset keeps Python and PostgreSQL
  matches equal for the supported forms. Where the engines still assign a
  capture differently, the result is a false disagreement (`rule_xcheck:<id>`
  fails, the rule is `not_run`), never a false pass.
- **Single-column node key.** The hierarchy node entity needs a one-column key.
- **Report separation.** report never reads `data_rules/result.json`; data-rule
  findings do not change its verdict.
- **No file of keys.** The keys a rule found are read from the database views;
  nothing writes them to a file.
- **No integration into other applications.** The rule model and the
  evaluator are used through this plugin's stages only in this release.
- Existing SQL, OWL, SHACL and synthetic-search limits remain, and no common
  Gold/Cube MVCC snapshot is created.
